# 结构层 · 编号系统与长篇不崩

> **百万字不断线的唯一秘诀：把记忆外包给表格。**
> LLM 上下文有限，人脑也记不住 400 章——但表格是无限的。

---

## 一、为什么长篇必崩（以及解法）

```yaml
崩的三个必然原因:
  1. 伏笔遗忘: 第 10 章埋的戒指，第 200 章忘了
  2. 数据漂移: 房贷 186 个月，第 150 章写成 168
  3. 爽点枯竭: 中段没料，只能注水

CDA 解法（把记忆外包）:
  1. 伏笔 → 编号表（F#/G# + 埋设章 + 回收章）
  2. 数据 → 硬数据校验表（每章对照）
  3. 爽点 → 事件库（提前备好 40+ 弹药）
```

## 二、伏笔编号系统（核心工具）

```yaml
超长篇（300万字+）用两级编号（见 09 号）:
  L 级（跨卷群长线，10-20条）: L1, L2...
  C 级（卷群内，每群5-10条）: C3-1（第3群第1条）
  标记: 新埋 L7 / 回收 C2-4

单本（100-200万字）用单级编号:
  每个项目独立编号（默者 F#，狂臣 G#）← 防串味
  - 每条伏笔: 编号 + 内容 + 埋设章 + 回收章 + 状态
  - 状态: 已埋 / 已回收 / 待回收

表格模板:
  | 伏笔 | 内容 | 埋设 | 回收 | 状态 |
  | F9 | 手上的伤疤 | 41 | 143 | 已回收 |
  | F10 | 主题句 | 1 | 400 | 待回收 |
```

### 伏笔三层设计

```yaml
长线伏笔（贯穿全书，5-10 条）:
  例: 主角身世之谜、终极反派身份、主题句
  → 卷一埋，卷四收

中程伏笔（单卷内，每卷 3-5 条）:
  例: 某个配角的秘密、某个道具的来源
  → 本卷埋，本卷收

短线伏笔（章内，每章可有）:
  例: 一句话、一个物件
  → 3-10 章内收，制造"草蛇灰线"感
```

### 伏笔健康度检查（每 10 章一次）

```yaml
□ 回收率 = 已回收 / 已埋设（应随进度上升）
□ 凭空回收 = 0（回收了但前文没埋 → 一票否决）
□ 重复埋设 = 0（同一伏笔埋两次 → 冗余）
□ 长线伏笔是否"还在呼吸"（每 30 章至少提及一次）
```

## 三、卷群架构（可生长骨架）

> **注：原"固定四卷 400 章"已升级为"卷群制"，详见 09 号文件。**
> 下面保留四卷作为"单个卷群内部"的参考节奏。

```yaml
卷群制（推荐）:
  一个卷群 = 一张地图 + 一个核心冲突 + 一个反派 + 一次阶段收束
  规模: 80-150 章
  关键: 每个卷群"可独立告一段落"，但留钩子指向下一群
  → 终点开放，可续可收（撑得起几百万字）

单个卷群内部（可用四卷节奏）:
  开群（10-20章）: 新地图/新反派/主角立足
  发展（40-80章）: 能力进阶、关系建立
  高潮（20-40章）: 决战、PV级名场面
  收束（10章）  : 反派倒台 + 阶段奖励 + 露出更大一层

冲突可持续（能不能长的关键）:
  套娃: 小BOSS → 大BOSS → 终极存在
  最强 = 体系不公 + 目标递进
  （"人"能打完，"规则"和"更大的世界"打不完）
```

### 卷内节奏（爽点分布）

```yaml
每章:   ≥1 个暗爽点（读者会心一笑）
每3章:  ≥1 个明爽点（反派吃瘪）
每卷:   3-5 个名场面（可截帧/可传播）
每10章: 1 个小高潮
每卷末: 1 个大高潮（PV 级）
```

## 四、逐章章纲（落地的施工图）

```yaml
章纲模板（每章必填）:
  章节编号: 卷X-章Y
  章名: （带钩子，≥5字，≤15字）
  摘要: （100 字，本章发生什么）
  暗爽点: （本章的爽点在哪）
  伏笔: 新埋 F# / 回收 F#
  情绪功能: （压抑/释放/转折/沉淀）
  字数类型: （静场/常规/反击/高潮）

作用:
  - LLM 按章纲扩写，不会跑偏
  - 章纲先行 → 批量生成 → 人工抽检
  - 章纲是"施工图"，正文是"装修"
```

## 五、爽点事件库（防中段枯竭）

```yaml
问题: 写到中段，套路用尽，开始注水

解法: 开工前备好 40+ 事件，分类轮换

四类事件库（模板）:
  A · 打压型（对方使坏）: 10 个
  B · 反击型（主角反杀）: 10 个
  C · 反转型（暗爽）:     10 个
  D · 共鸣型（情绪）:     10 个

轮换规则:
  - 不连续两章用同一类
  - A 后必跟 B（打压→反击）
  - D 每 5-8 章一次（调节情绪）
  - C 用于"看似要输"的翻转
```

## 六、硬数据校验表（数据连续性）

```yaml
必校验数据（每章对照）:
  □ 主角年龄/身份
  □ 家庭成员姓名（妻: 林晚 / 女: 朵朵）
  □ 关键数字（房贷 186→172 递减、工号 005）
  □ 时间线（事件先后顺序）
  □ 地名/机构名（无错别字、无前后不一）
  □ 角色称谓（同章内统一）

方法:
  - 建一张"硬数据表"放在 prompt 里
  - 每章生成后自动对照
  - 错一处即打回
```

## 七、防注水（长篇最大杀手）

```yaml
注水的三个信号:
  1. 章节无"暗爽点"（只是推进剧情）
  2. 对话无信息量（角色在说废话）
  3. 环境描写 > 300 字（为凑字数）

CDA 防注水机制:
  □ 字数按类型浮动，不设死数
  □ 结束条件是"卡点"，不是"写满字数"
  □ 每章必须有暗爽点（无则打回）
  □ 环境描写 ≤300 字（超则删）
  □ 每章必须有"信息增量"（新伏笔/新反转/新数据）
```

## 八、一句话总结

> **长篇不崩，靠的不是记性好，是表格全。**
> 伏笔编号化、数据表格化、爽点库存化、章纲施工化。
> **把记忆外包给工具，人脑只做判断。**
